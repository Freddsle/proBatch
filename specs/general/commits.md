# Commit messages

## Goal of the document

This document describes the required format and content of Git commit messages generated for proBatch.

## Scope

The scope of this specification includes commit messages drafted, proposed, created, amended, or otherwise generated by agents for new project commits.

Existing commit history, Git-generated merge messages, branch naming, pull-request titles, release-note formatting, and authorization to create or rewrite commits are out of scope.

## Dictionary

- `header` — the mandatory first line of a commit message.
- `type` — the category of change expressed at the start of the header.
- `scope` — an optional stable project area affected by the change.
- `description` — the concise summary following the type and optional scope.
- `breaking change` — a change that requires users or downstream code to adapt because a public contract is no longer backward compatible.
- `footer` — a Git-trailer-style record following the optional commit body.

## Convention

All agent-generated commit messages MUST follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).

The required structure is:

```text
<type>[optional scope][optional !]: <description>

[optional body]

[optional footer(s)]
```

This convention applies prospectively. Existing commits MUST NOT be rewritten solely to conform to it.

## Header

The header MUST contain an allowed type, an optional scope, an optional breaking-change marker, a colon followed by one space, and a nonempty description.

The header MUST NOT exceed 100 characters and SHOULD remain at or below 72 characters when clarity permits.

### Types

The type MUST be one of:

- `feat` — adds or changes user-visible package functionality or a public API.
- `fix` — corrects incorrect package behavior.
- `docs` — changes editable documentation only, including specifications, README content, vignettes, or Roxygen2 comments under `./R/`.
- `test` — adds or changes tests without changing package behavior.
- `refactor` — restructures implementation without changing intended behavior.
- `perf` — improves performance without changing intended behavior.
- `build` — changes package build metadata, declared dependencies, or build configuration.
- `ci` — changes continuous-integration configuration.
- `style` — changes formatting or whitespace without changing behavior.
- `chore` — performs repository maintenance or tooling work that fits no more specific type.
- `revert` — reverts an earlier commit.

`feat` and `fix` MUST be reserved for changes observable by package users. Specification or tooling changes MUST NOT use `feat` unless they also introduce user-visible package functionality.

Version-only and release-maintenance commits SHOULD use `chore(release)`.

### Scope

A scope MAY identify the principal package area or project subsystem affected by the commit.

A scope MUST use lowercase letters, digits, and hyphens, MUST begin with a letter or digit, and MUST remain concise.

Stable scopes SHOULD be preferred, such as `normalization`, `plots`, `pbf`, `missing-data`, `package`, `vignettes`, `specs`, `workflows`, or `depmesh`.

A scope MUST NOT list multiple files or repeat information already clear from the type and description. A coherent cross-cutting change MAY omit the scope.

### Description

The description MUST use the imperative present tense, describe the resulting change, begin with a lowercase word unless a case-sensitive project name or R symbol must appear first, and omit a trailing period.

The description MUST be specific enough to distinguish the commit from unrelated work. Generic descriptions such as `update files`, `misc changes`, `fix issues`, or `work in progress` MUST NOT be used.

Issue identifiers, test results, and implementation detail lists SHOULD NOT appear in the header.

## Body

A body MAY follow the header after one blank line.

The body SHOULD explain why the change is needed, relevant behavior before and after the change, and consequences that are not obvious from the diff.

The body MUST NOT merely repeat the header. It MUST use complete sentences when present.

## Footers

Footers MAY follow the body, or the header when no body is present, after one blank line.

Footers MUST use Git-trailer-compatible `Token: value` syntax except for the Conventional Commits `BREAKING CHANGE: description` token.

An agent MUST NOT invent an issue, pull request, author, reviewer, or sign-off reference. Reference footers MAY be included only when the relevant identifier or attribution is known from project context or supplied by the user.

## Breaking changes

A breaking change MUST place `!` immediately before the header colon and MUST include a `BREAKING CHANGE:` footer that explains the incompatible contract and required migration.

The type MUST still describe the nature of the change. Breaking changes are not a separate type.

Example:

```text
feat(pbf)!: change assay naming convention

Use level-qualified assay names consistently across transformation pipelines.

BREAKING CHANGE: callers must replace unqualified assay names with `<level>::<pipeline>` names.
```

## Agent requirements

Before drafting or creating a commit message, an agent MUST inspect the exact staged change or the explicit change summary provided by the user.

An agent MUST choose the type from the change’s effect, not from the filenames modified.

A commit SHOULD contain one coherent change. If the staged diff contains unrelated changes that cannot be described accurately by one header, the agent MUST report that the commit should be split rather than generate a misleading message.

When an agent proposes multiple candidate messages, every candidate MUST comply with this specification.

An agent MUST validate the final header against the required structure, allowed type, scope syntax, length limit, imperative description, and breaking-change rules before presenting or using it.

This specification governs message format only. An agent MUST NOT create, amend, squash, or rewrite a commit unless the user has authorized that Git action.

## Examples

Valid headers:

```text
feat(normalization): add median-centering pipeline
fix(missing-data): preserve assay names when filtering
docs(specs): require conventional commit messages
test(pbf): cover batch-step registration
refactor(plots): share annotation color handling
build(package): update Bioconductor dependencies
chore(depmesh): exclude generated manuals
chore(release): bump development version
```

Invalid headers:

```text
Update normalization
feature: add normalization
feat: Added normalization.
fix: misc changes
docs(Specs): update rules
```

The invalid examples respectively omit a type, use an unsupported type, use past tense and a trailing period, use a vague description, and use an uppercase scope.
